# ReproCheck 术语字典（面向新用户）

日期：2026-11-24  
用途：把专业词保留为“可对照原文”的原词，同时给出一句任务语言解释。页面中悬停/聚焦术语按钮即可看到；手册第 9 章也使用同一套定义。  
原则：不为了通俗而丢掉科研准确性；不把“证据不足”说成“已验证”。

| 术语 | 一句话解释（页面用） | 更完整的解释 | 常见别名 |
|---|---|---|---|
| 科研复现 | 照着论文再做一遍实验，看看结论能不能站得住。 | 不是把论文复述一遍，而是把论文里的数据、代码、实验环境和结果逐项对齐，记录哪些能重现、哪些不能、为什么。 | 复现、可复现性、reproducibility |
| 论文 | 你要核对的那篇研究报告。 | 通常上传 PDF。ReproCheck 会保存原文，并尝试提取标题、方法、数据与结果等信息；提取结果需要你复核。 | Paper、文献 |
| 数据集 | 论文实验所用的原始数据或表格。 | 例如 CSV、Excel。数据集是判断结果能否复现的重要证据；没有数据时可以先跳过，之后再补。 | Dataset、数据 |
| 代码仓库 | 作者存放实验代码的网页地址。 | 例如 GitHub、GitLab 或 Gitee 链接。ReproCheck 只登记地址，不会自动下载或运行仓库里的代码。 | Repository、Repo、代码库 |
| 实验环境 | 跑实验时电脑里的软件和版本组合。 | 包括 Python 版本、依赖包、显卡/系统等。环境不同，结果可能不同，所以要记录并检查缺失项。 | Environment、运行环境 |
| 软件依赖 | 实验运行前必须安装的软件包。 | 例如 requirements.txt 里列出的包。缺少依赖时实验可能直接失败，或算出不同结果。 | Dependency、依赖包 |
| API | 让两个软件互相通信的接口。 | ReproCheck 用 API 连接外部 AI 服务，辅助整理与抽取；它不是验证论文真实性的替代品，也不影响你保存和整理材料。 | 接口、应用程序接口 |
| API 密钥 | 服务商发给你的一串访问凭证。 | 类似一把只给你用的钥匙。不要发给别人，也不要写进论文、代码仓库或聊天截图。 | API Key、密钥、Key |
| 模型 | 实际帮你阅读和整理内容的 AI 程序。 | 不同模型在速度、费用、中文能力和可处理长度上不同；需要先在服务商处开通，并在测试连接成功后才能使用。 | Model、大模型 |
| 服务地址 | AI 服务所在的网址。 | 高级设置。一般选择服务商后自动带出默认地址，只有自建服务或代理服务才需要改。 | Base URL、Endpoint、接口地址、端点 |
| 模型名称 | 你要调用的那个 AI 模型的名字。 | 不同服务商不同，通常从控制台或文档复制；填错时测试会提示“找不到模型”。 | Model ID、模型 ID |
| 温度参数 | 控制 AI 回答“稳定”还是“发散”的旋钮。 | 高级设置。越低越稳定、越可重复；越高越发散。科研材料整理建议保持默认的低值。 | Temperature |
| 最大输出长度 | 一次最多允许 AI 写多长。 | 高级设置。太小会截断，太大可能增加费用；不确定时保留默认。 | Max Tokens、输出上限 |
| 请求超时 | 等待服务商多久还没回应就算失败。 | 高级设置。网络慢时可适当增大；过长会让失败反馈来得更晚。 | Timeout |
| 证据 | 能指回论文原文的依据。 | 每条科研事实都应能定位到具体材料、页码或段落。没有证据的说法只能标为“待复核”或“证据不足”。 | Evidence、原文依据 |
| 科研事实 | 从论文中抽出的一条可核对信息。 | 例如数据集名称、模型结构、实验指标。它不是 AI 的自由发挥，应附原文位置并允许人工修订。 | Fact、事实 |
| 证据图谱 | 把事实、原文和它们之间的关系连起来看。 | 用于检查一条结论是否有足够依据，以及不同材料之间是否矛盾。 | Evidence Graph、证据关系图 |
| 复现规划 | 把复现拆成可执行的步骤清单。 | 每个任务写明要做什么、依赖什么、是否需要人工确认。它不会自动替你运行代码。 | Plan、DAG、规划 |
| 复现运行 | 真正执行一次复现任务。 | 运行可能成功、失败或被安全策略阻止。执行记录保留时间、输出和错误。 | Run、执行 |
| 结果对照 | 把论文报告的结果和你的复现结果放在一起比较。 | 关注指标、误差和差异原因。对照不等于自动判定谁对谁错，需要结合证据判断。 | Comparison、结果比较 |
| 审计报告 | 把这次复现的过程、证据和结论整理成一份可交付文档。 | 汇总材料、事实、运行与对照结果。可导出，但不应把“未验证”写成“已证实”。 | Report、复现报告 |
| 操作与审计记录 | 谁在什么时候做了什么。 | 用于团队复核和追溯，不会因刷新丢失。普通使用者通常只需查看，不需要修改。 | Audit Trail、审计轨迹 |
| 数据来源记录 | 这份材料从哪里来、经过了哪些处理。 | 包括上传文件、原文位置、抽取方式和修改记录，帮助别人判断证据是否可靠。 | Provenance、溯源 |
| 对照测试 | 用一组已知答案的案例来检查系统是否可靠。 | 基准案例库中的案例是测试材料，不代表你自己的科研结论。 | Benchmark、基准 |

## 页面上的术语替换

| 旧文案 | 新文案 | 保留技术词的位置 |
|---|---|---|
| 项目工作台 / Bloom 项目工作台 | 项目总览图 | 页面内部仍可看到 Bloom 说明 |
| 材料管理 | 论文与材料 | 材料类型仍使用“代码仓库链接”等原词 |
| 解析任务 | 自动处理任务 | 任务详情可展开“解析状态” |
| 证据图谱 | 证据关系图 | 术语表保留“证据图谱 / Evidence Graph” |
| 复现规划 DAG | 复现步骤清单 | 高级页保留 DAG 节点/依赖说明 |
| 复现环境 | 实验环境 | 依赖/系统/硬件原词保留 |
| 报告中心 | 审计报告 | 报告详情仍使用 Report |
| 模型管理中心 | 连接 AI 助手 | 高级管理模式保留服务商/端点/模型 ID |
| provider / endpoint / capability | 服务商 / 服务地址 / 能力 | 技术详情和高级设置中保留原词 |

## 不做的“通俗化”

- 不把“证据不足”改成“通过”；
- 不把“未运行”改成“已完成”；
- 不把“代码仓库已登记”写成“代码已复现”；
- 不把 API 测试失败写成“网络问题”掩盖密钥错误；
- 不把复杂技术能力删掉，只折叠到第二层。
